## 1. 问题现象

一台刷了 LineageOS 18.1 GSI 的平板，3.5mm 耳机口出问题，症状随时间推移呈现出**三种不同状态**，这本身是重要线索：

| 阶段 | 现象 |
|------|------|
| 初始 | 插入耳机，**完全无声**（耳机没声、平板扬声器也没声） |
| 中期 | 手动调过 mixer 后，**耳机和平板同时出声** |
| 后期 | mixer 回滚后，**耳机响、平板也响**（双路输出） |

> **关键判断**：症状会"变"，说明**不是断线、不是焊点脱落**。
> 纯硬件损坏不会因为软件操作改变表现。问题在软件层（路由/检测），硬件通路是好的。

连带的历史改动：此前为了修蓝牙音频，关过 A2DP offload（`persist.sys.phh.disable_a2dp_offload=true`），这个改动与耳机问题无因果关系，但排查时要排除掉。

## 2. 先搞清楚：这到底是不是硬件坏了

**做任何软件修复前，必须先证明硬件通路是通的。** 否则可能在错误的层面上折腾一整天。

### 2.1 确认设备身份与系统分层

```bash
adb shell getprop ro.product.model
adb shell getprop ro.build.version.release        # 11
adb shell getprop ro.vendor.build.version.release # 10  ← vendor 是原厂 Android 10
adb shell getprop ro.build.type                   # userdebug
adb shell getprop ro.debuggable                   # 1
```

本机结论：**system = Android 11 (SDK 30)，vendor = 原厂 Android 10 (SDK 29)，VNDK 29**。
这是典型的 GSI 混搭，音频 HAL 是原厂的，框架是 AOSP 的——**两者对接口的理解可能有版本差**，这是后面问题的土壤。

### 2.2 确认 vendor 驱动没丢

```bash
adb shell getprop ro.vendor.build.fingerprint   # 应含 release-keys
adb shell ls /vendor/lib/hw/ | grep audio       # 应有 audio.primary.default.so
adb shell ls /vendor/lib64/hw/ | grep audio
```

本机 `ro.vendor.build.tags=release-keys`，驱动完整。
→ **可以否定"从官方固件提取驱动"的思路**，这条路不用走。

### 2.3 直接验证硬件通路：手动开功放

这是决定性的一步。用 `tinymix` 手动打开耳机通路，如果耳机能出声，就证明 **DAC → 耳机座 → 耳机** 整条模拟链路完好。

```bash
adb shell tinymix -D 0     # 列出所有控件，先看清楚有什么
```

本机（MTK 音频 codec）关键控件：

| 控件 ID | 名称 | 作用 |
|---------|------|------|
| 3 | `Speaker_Amp_Switch` | 扬声器功放 |
| — | `Audio_Amp_L_Switch` / `Audio_Amp_R_Switch` | 主音频功放左右声道 |
| — | `Headset_Speaker_Amp_Switch` | **耳机/扬声器共用主功放**（重点！） |
| — | `Headset_PGAL_GAIN` / `Headset_PGAR_GAIN` | 耳机 PGA 增益 |
| — | `Headphone Plugged In` | 耳机插入状态（只读） |
| — | `DAC_LOOP_DAC_HP` / `DAC_LOOP_DAC_HS` | DAC 回环测试 |

手动测试命令：

```bash
adb shell tinymix 3 On                      # 开扬声器功放
adb shell tinymix "Audio_Amp_L_Switch" On
adb shell tinymix "Audio_Amp_R_Switch" On
adb shell tinymix "Headset_Speaker_Amp_Switch" On
adb shell tinymix "Headset_PGAL_GAIN" 2Db
adb shell tinymix "Headset_PGAR_GAIN" 2Db
adb shell -c "setprop ctl.restart audioserver"   # 或者直接 play 一段音乐
```

> **实测结果：耳机出声了。**
> → 硬件通路 100% 完好。问题锁定在**软件路由**。

### 2.4 血泪教训：混音器不要乱动

测试过程中我曾把 `Speaker_Amp_Switch` 关掉（以为能"静音扬声器只留耳机"），结果**两边全哑**。

原因：`Headset_Speaker_Amp_Switch` 是**耳机和扬声器共用的主功放**，把 `Speaker_Amp_Switch` 关掉后整个输出被切断，耳机也跟着没声。

**正确做法**：不要试图通过 mixer 混音器"手动切路由"。混音器是底层开关，路由应该由上层 AudioPolicy 决策。混音器只用于**验证硬件**，验证完必须完整回滚。

完整回滚命令：

```bash
adb shell tinymix 3 Off
adb shell tinymix "Audio_Amp_L_Switch" Off
adb shell tinymix "Audio_Amp_R_Switch" Off
adb shell tinymix "Headset_Speaker_Amp_Switch" Off
adb shell tinymix "Headset_PGAL_GAIN" 2Db
adb shell tinymix "Headset_PGAR_GAIN" 2Db
adb shell -c "setprop ctl.restart audioserver"
```

## 3. 定位根因：四层链路逐一排查

Android 有线耳机从"物理插入"到"声音从耳机出来"，要经过 **4 层**。任何一层断了都会表现为"耳机无声"。

```
┌─────────────┐   ①物理检测    ┌──────────────┐   ②input上报   ┌────────────────┐
│  3.5mm 座    │ ─────────────> │ MTK ACCDET   │ ─────────────> │ InputReader    │
│  插头/簧片   │                │ 驱动 (kernel) │                │ SwitchValues   │
└─────────────┘                └──────────────┘                └────────────────┘
                                                                        │
                                                                        │ ③广播
                                                                        ▼
┌─────────────┐   ⑥HAL执行    ┌──────────────┐   ⑤切设备      ┌────────────────┐
│  Audio HAL  │ <───────────── │ AudioPolicy  │ <───────────── │ WiredAccessory │
│ (vendor)    │                │  (system)    │                │ Manager        │
└─────────────┘                └──────────────┘                └────────────────┘
       │
       │ ⑦功放/DAC
       ▼
   耳机出声
```

### 3.1 第一层：MTK ACCDET 驱动检测

MTK 平台的耳机检测由 **ACCDET**（Accessory Detect）完成。

```bash
adb shell getprop | grep -i accdet
adb shell ls /sys/bus/platform/drivers/Accdet_Driver/
```

本机节点：

| 文件 | 含义 |
|------|------|
| `state` | 当前检测状态：**0 = 无，2 = 已插入**（实测值） |
| `dump_reg` | 寄存器快照，深度调试用 |
| `set_headset_mode` | 手动设置耳机模式（4 段/3 段） |

**插上耳机后读取：**

```bash
adb root
adb shell cat /sys/bus/platform/drivers/Accdet_Driver/state
# 输出: 2
```

> ✅ **第一层通过**：ACCDET 驱动正确检测到了插入。

同时确认输入设备声明了正确的 switch 位：

```bash
adb shell getevent -pl /dev/input/event0
```

输出：

```
add device 1: /dev/input/event0
  name:     "ACCDET"
  events:
    KEY (0001): KEY_VOLUMEDOWN  KEY_VOLUMEUP  KEY_PLAYPAUSE  KEY_VOICECOMMAND
    SW  (0005): SW_HEADPHONE_INSERT*  SW_MICROPHONE_INSERT  SW_LINEOUT_INSERT  SW_JACK_PHYSICAL_INS
```

> ✅ 驱动声明了 `SW_HEADPHONE_INSERT`（带 `*` 表示当前置位）。
> **注意这个 `*` 是误导**——它表示"该能力被支持"，不代表每次都能上报正确的值。第三层会看到问题。

### 3.2 第二层：内核 config

```bash
adb shell zcat /proc/config.gz | grep -E "CONFIG_SWITCH|CONFIG_MTK_ACCDET"
```

本机结果：

```
# CONFIG_SWITCH is not set     ← 通用 switch 子系统没编进去
CONFIG_MTK_ACCDET=y            ← 但 MTK 自己的 ACCDET 在
```

结论：**不影响**。ACCDET 走自己的一套 input 上报路径，不依赖 `CONFIG_SWITCH`。

### 3.3 第三层：InputReader 上报的 SwitchValues（← 问题在这里）

这是整个排查的核心命门。InputReader 汇总所有 switch 位成一个整数值，广播给上层。

```bash
adb shell dumpsys input | grep -i "SwitchValues"
```

**耳机插入状态下输出：**

```
SwitchValues: 4
```

对比 Android 的 switch 位定义（`frameworks/native/include/input/Input.h`）：

| 位 | 值 | 常量 |
|----|-----|------|
| bit0 | 1 | `SW_HEADPHONE_INSERT` ← **耳机插入，必须置位** |
| bit1 | 2 | `SW_MICROPHONE_INSERT` ← 带麦耳机（4 段） |
| bit2 | 4 | `SW_LINEOUT_INSERT` |
| bit3 | 8 | `SW_JACK_PHYSICAL_INSERT` |

> ❌ **`SwitchValues = 4` 说明只有 `SW_LINEOUT_INSERT` 置位了，`SW_HEADPHONE_INSERT`（bit0 = 1）从未置位！**
>
> 这就是根因所在：**底层检测到了插入（state=2），但上报给上层时用错了 switch 位。**

补充证据——`WiredAccessoryManager` 从未被触发：

```bash
adb shell dumpsys audio | grep -A5 "wired/A2DP/hearing aid device connection"
```

输出里只有蓝牙 A2DP 的连接记录，**没有任何有线设备的连接事件**。正常系统在插耳机时会记录类似：

```
setWiredDeviceConnectionState( type:8 state:DEVICE_STATE_AVAILABLE ...)
```

> ❌ 一条都没有 → 确认上层完全不知道耳机插入了。

### 3.4 第四层：AudioPolicy 输出设备列表

```bash
adb shell dumpsys audio | grep "Devices:"
```

问题状态下只有 `speaker`，没有 `headphone`。确认：AudioPolicy 认为只有扬声器可用。

## 4. 根因结论

**一句话：ACCDET 驱动检测到了耳机插入，但上报的 switch 位是 `SW_LINEOUT_INSERT`(4) 而不是 `SW_HEADPHONE_INSERT`(1)，导致 `WiredAccessoryManager` 不认为有耳机插入，因此 AudioPolicy 不切换音频路由，音频继续走扬声器。**

完整因果链：

```
ACCDET 检测到插入 (state=2)   ✅
        ↓
InputReader 上报 SwitchValues=4  ❌ 应该是 1（或 5）
        ↓
WiredAccessoryManager 只认 SW_HEADPHONE_INSERT(bit0)
        ↓ 不触发
AudioService.setWiredDeviceConnectionState 从未被调用
        ↓
AudioPolicy 的可用设备列表里没有 WIRED_HEADPHONE
        ↓
Audio HAL 不关闭扬声器、不打开耳机通路
        ↓
现象：耳机无声 / 或耳机和扬声器同时出声（取决于 mixer 状态）
```

**为什么修不了 kernel**：ACCDET 是编译进 vendor 的驱动（`CONFIG_MTK_ACCDET=y`），没有源码、没有 vendor 编译环境，改不了上报逻辑。

**为什么修不了 system 层的 WiredAccessoryManager**：GSI 的 system 是只读 dm-verity 分区，且改 framework 需要重新编译整个 system image。

→ **只能在应用层"补发"这个缺失的事件。**

## 5. 正常系统是怎么做的（原理）

理解这一点，才能理解为什么我们的修复方案要这么设计。

### 5.1 正常流程

```
InputReader (native)
  └─ 检测到 switch 变化，打包成 Event
       └─ 通过 InputManagerService 广播
            └─ WiredAccessoryManager（system_server，Java）
                 └─ 识别 SW_HEADPHONE_INSERT
                      └─ 调用 AudioService.setWiredDeviceConnectionState(
                             AudioDeviceAttributes(ROLE_OUTPUT, TYPE_WIRED_HEADPHONES, ""),
                             DEVICE_STATE_AVAILABLE,
                             "WiredAccessoryManager")
                           └─ AudioPolicyManager 切设备
                                └─ Audio HAL 关 speaker、开 headphone
```

### 5.2 我们要补的就是 `setWiredDeviceConnectionState` 这一调

关键 API（`IAudioService`）：

```java
void setWiredDeviceConnectionState(AudioDeviceAttributes attributes, int state, String caller);
```

在 AOSP Android 11 上，这个 binder 事务号是 **64**，参数布局是：

```
writeInterfaceToken("android.media.IAudioService")
writeTypedObject(AudioDeviceAttributes, 0)    // role(2=OUTPUT), type(4=TYPE_WIRED_HEADPHONES), address("")
writeInt(state)                                // 1 = AVAILABLE, 0 = UNAVAILABLE
writeString(caller)                            // 调用者标识，随便写
```

## 6. 修复方案演进：为什么最后选了 APK

走过的弯路值得记录，能帮别人少花时间。

### 方案 A：`cmd audio` 命令行

```bash
adb shell cmd audio
```

→ `No shell command implementation`。Android 11 的音频服务没有 shell command 实现。

```bash
adb shell cmd media.audio_policy
```

→ 只有 `uid-state` 子命令，没有设置设备连接状态的能力。

**❌ 死在第一步。**

### 方案 B：`app_process` 跑 Java（免安装）

思路：用 `app_process` 直接跑一段 Java，反射调 `AudioManager`。

```bash
adb shell app_process -Djava.class.path=/data/local/tmp/fix.jar /system/bin com.abnen.WireFix
```

→ **`Aborted`**。backtrace：

```
jniRegisterNativeMethods → FindClass → AssertNoPendingException → abort
```

GSI 上的 `app_process` 与 `RuntimeInit` 不匹配，一跑就崩。

换 `dalvikvm`：

```bash
adb shell dalvikvm -cp /data/local/tmp/fix.jar com.abnen.WireFix
```

→ Java 能跑，但 `ServiceManager.<clinit>` 报：

```
UnsatisfiedLinkError: SystemProperties.native_get_int
```

**❌ 死于 GSI 的 app_process 环境问题。**

### 方案 C：普通 App 反射调用

装一个普通 App，反射调 `AudioManager.setWiredDeviceConnectionState(...)`。

结果：

```
java.lang.NoSuchMethodException:
  android.media.AudioManager.setWiredDeviceConnectionState[...]
```

这是 **Android 的 Hidden API 限制**——非 SDK 接口被 `getMethod` 直接屏蔽（不是抛异常，是"假装不存在"）。

想用标准绕法：

```java
Class<?> vmr = Class.forName("dalvik.system.VMRuntime");
Method setEx = vmr.getDeclaredMethod("setHiddenApiExemptions", String[].class);
setEx.invoke(vmr.getMethod("getRuntime").invoke(null), (Object) new String[]{"L"});
```

→ `NoSuchMethodException: VMRuntime.setHiddenApiExemptions`
**Phh 的 GSI 把这个方法删了。**

**❌ Hidden API 路线彻底堵死。**

### 方案 D（最终）：Parcel + IBinder 直连 + priv-app 提权

**两个关键突破：**

**突破 1：绕开反射，直接走 binder。**
`Parcel`、`IBinder.transact` 都是**公开 SDK API**，不受 Hidden API 限制。

```java
Parcel data = Parcel.obtain();
Parcel reply = Parcel.obtain();
data.writeInterfaceToken("android.media.IAudioService");
data.writeInt(8);           // device
data.writeInt(1);           // state
data.writeString("");       // address
data.writeString("WireFix"); // caller
b.transact(64, data, reply, 0);
reply.readException();
```

`ServiceManager.getService("audio")` 是 greylist（灰色名单）——可以调，只打警告不拦截。如果被拦，还有 meta-reflection 兜底：

```java
Method meta = Class.class.getDeclaredMethod("getDeclaredMethod", String.class, Class[].class);
gs = (Method) meta.invoke(ServiceManager.class, "getService", new Class[]{String.class});
```

**突破 2：`MODIFY_AUDIO_ROUTING` 需要特权。**
即使 binder 通了，服务端还会检查权限：

```
SecurityException: Missing MODIFY_AUDIO_ROUTING permission
```

这个权限的 protectionLevel 是 `signature|privileged`——只有系统签名应用或 `/system/priv-app` 下的应用能拿。

→ 用 **Magisk systemless 模块**把 APK 挂载为 priv-app（不改 system 分区、可随时删除回滚）。

**✅ 方案 D 成功。**

## 7. 完整实施步骤

### 前置条件

| 项 | 要求 |
|----|------|
| Root | Magisk 20+ （实测 28.0） |
| 系统 | Android 10+ （实测 11） |
| adb | 已连接、可 `adb root` |
| 设备 | MTK 平台（ACCDET 路径依赖 MTK） |

> **非 MTK 设备注意**：`/sys/bus/platform/drivers/Accdet_Driver/state` 是 MTK 专有路径。
> 高通/其他平台需要换检测源（见文档末尾"移植到其他平台"）。

### Step 1 — 环境准备

```bash
# 确认 root
adb root
adb shell id        # 应显示 uid=0(root)

# 确认 Magisk
adb shell su -c "magisk -v"
# 28.0:MAGISK:R

adb shell su -c "ls /data/adb/modules"
# zygisk_lsposed  ← 已有模块说明 Magisk 工作正常
```

### Step 2 — 部署 APK 到 priv-app

**方式一：一键脚本（推荐）**

```bash
adb push WireFix-kit /data/local/tmp/
adb shell su -c "sh /data/local/tmp/WireFix-kit/scripts/install.sh"
adb reboot
```

Windows 用户直接双击 `scripts/install-windows.bat`。

**方式二：手动逐步（理解流程用）**

```bash
# 1) 推到临时目录
adb push WireFix.apk /data/local/tmp/WireFix.apk

# 2) 建模块目录
adb shell su -c "mkdir -p /data/adb/modules/wirefix/system/priv-app/WireFix"
adb shell su -c "mkdir -p /data/adb/modules/wirefix/system/etc/permissions"

# 3) 放 APK
adb root
adb push WireFix.apk /data/adb/modules/wirefix/system/priv-app/WireFix/WireFix.apk
adb shell chmod 644 /data/adb/modules/wirefix/system/priv-app/WireFix/WireFix.apk

# 4) 修 SELinux 标签（关键！不修 PMS 读不到）
adb shell chcon u:object_r:system_file:s0 \
  /data/adb/modules/wirefix/system/priv-app/WireFix/WireFix.apk

# 5) 权限白名单
adb shell su -c 'cat > /data/adb/modules/wirefix/system/etc/permissions/privapp-permissions-wirefix.xml << "EOF"
<?xml version="1.0" encoding="utf-8"?>
<permissions>
    <privapp-permissions package="com.abnen.wirefix">
        <permission name="android.permission.MODIFY_AUDIO_ROUTING" />
        <permission name="android.permission.MODIFY_AUDIO_SETTINGS" />
        <permission name="android.permission.FOREGROUND_SERVICE" />
    </privapp-permissions>
</permissions>
EOF'
adb shell chmod 644 /data/adb/modules/wirefix/system/etc/permissions/privapp-permissions-wirefix.xml
adb shell chcon u:object_r:system_file:s0 \
  /data/adb/modules/wirefix/system/etc/permissions/privapp-permissions-wirefix.xml

# 6) module.prop
adb shell su -c 'cat > /data/adb/modules/wirefix/module.prop << "EOF"
id=wirefix
name=WireFix 耳机路由修复
version=1.0
versionCode=1
author=zhuanjia
description=修复 3.5mm 有线耳机无声
EOF'

# 7) 卸载可能冲突的用户层应用
adb shell pm uninstall com.abnen.wirefix

# 8) 重启
adb reboot
```

### Step 3 — 验证 APK 已成为特权应用

重启后等 1~2 分钟（首次开机要扫描新包）：

```bash
adb shell pm path com.abnen.wirefix
# package:/system/priv-app/WireFix/WireFix.apk     ← 必须是这个路径

adb shell dumpsys package com.abnen.wirefix | grep MODIFY_AUDIO_ROUTING
# android.permission.MODIFY_AUDIO_ROUTING
# android.permission.MODIFY_AUDIO_ROUTING: granted=true     ← 必须是 true
```

> 如果 `pm path` 报"找不到包"，看 §8 坑 1、坑 2。

### Step 4 — 部署自动守护脚本

```bash
# 复制脚本
adb root
adb push service.sh /data/adb/modules/wirefix/service.sh
adb shell chmod 755 /data/adb/modules/wirefix/service.sh
adb shell chcon u:object_r:system_file:s0 /data/adb/modules/wirefix/service.sh

adb reboot
```

脚本内容（`module/service.sh`）：

```sh
#!/system/bin/sh
# 轮询 ACCDET 状态，变化时拉起 GuardService
SLEEP=2
last=""
while true; do
    s=$(cat /sys/bus/platform/drivers/Accdet_Driver/state 2>/dev/null)
    if [ -n "$s" ] && [ "$s" != "$last" ]; then
        if am start-foreground-service -n com.abnen.wirefix/.GuardService \
               --ei state "$s" >/dev/null 2>&1; then
            last=$s          # ← 只有 am 成功才更新，否则下轮重试
        fi
    fi
    sleep $SLEEP
done
```

**为什么用 `am start-foreground-service` 而不是广播？**
→ 见 §8 坑 4（Android 11 后台广播限制）。

**为什么 `last` 要在 `am` 成功后才更新？**
→ 见 §8 坑 5（开机时 AMS 未就绪会永久漏发）。

## 8. 踩过的坑（重要，别人一定会遇到）

这一节是整份文档最有价值的部分。每个坑我都实际踩过。

### 坑 1：Magisk 模块目录里的 `update` 文件会让模块**完全不挂载**

我在创建模块时随手 `touch $MOD/update`，结果重启后 `/system/priv-app/WireFix` 是空的。

**Magisk 的语义**：`/data/adb/modules/<id>/update` 存在时，表示"模块待更新"，Magisk **跳过挂载**。这是给 Magisk Manager 用的标记，手动创建模块时**绝对不能有**。

```bash
rm -f /data/adb/modules/wirefix/update
```

### 坑 2：`adb push` 到模块目录的文件 SELinux 标签是 `adb_data_file`，`system_server` 读不到

现象：

```
avc: denied { getattr } for path="/system/priv-app/WireFix/WireFix.apk"
     scontext=u:r:system_server:s0 tcontext=u:object_r:adb_data_file:s0
avc: denied { read } for name="WireFix.apk" ... tclass=file
```

PMS（PackageManagerService）扫描时被 SELinux 拒绝，包直接"消失"——`pm path` 返回空，`am start` 报 `Activity class does not exist`。

**必须手动改标签：**

```bash
chcon u:object_r:system_file:s0 /data/adb/modules/wirefix/system/priv-app/WireFix/WireFix.apk
chcon u:object_r:system_file:s0 /data/adb/modules/wirefix/system/etc/permissions/privapp-permissions-wirefix.xml
chcon u:object_r:system_file:s0 /data/adb/modules/wirefix/service.sh
```

> 验证：`ls -Z` 看标签，应为 `u:object_r:system_file:s0`。

### 坑 3：`service.sh` 用子 shell `&` 会被 magiskd 杀掉

错误写法：

```sh
(
while true; do ... done
) &          # ← 子 shell 后台，service.sh 退出后进程组被清理
```

现象：Magisk 日志显示 `wirefix: exec [service.sh]` 执行了，但 `ps` 里找不到循环进程。

**正确写法**：直接把循环写在顶层，`service.sh` 本身常驻。

```sh
SLEEP=2
while true; do ... sleep $SLEEP; done
```

### 坑 4：Android 11 禁止向 manifest receiver 发送后台广播

我先用 `am broadcast -a com.abnen.wirefix.ACCDET_STATE --ei state 2`，结果：

```
W BroadcastQueue: Background execution not allowed:
   receiving Intent { act=com.abnen.wirefix.ACCDET_STATE ... } to com.abnen.wirefix/.StateReceiver
```

Android 8 起对隐式广播有后台限制，即使接收方是自家 manifest 注册的 receiver 也会被拦。

**解法**：改用 `am start-foreground-service`。**root 身份调用时不受后台启动限制**，而且前台服务本身就允许长期运行。

```sh
am start-foreground-service -n com.abnen.wirefix/.GuardService --ei state "$s"
```

### 坑 5：开机时 AMS 还没起来，`am` 静默失败，状态却被记住了

第一版脚本：

```sh
s=$(cat .../state)
if [ "$s" != "$last" ]; then
    last=$s                                 # ← 先记住
    am start-foreground-service ...         # ← 后调用，开机时这里失败
fi
```

开机时 `service.sh` 在 `boot-complete` 之前就跑起来了，此时 ActivityManager 还没准备好，`am` 返回非 0。但 `last` 已经被设成 2，之后**永远不会再补发**。

现象：手动跑脚本有效，开机自动跑无效。

**解法**：`am` 成功才更新 `last`。

```sh
if am start-foreground-service ... >/dev/null 2>&1; then
    last=$s
fi
```

### 坑 6：事务号 64 是对的，但 Parcel 布局不是 AOSP 文档写的那样

AOSP Android 11 的 `IAudioService.setWiredDeviceConnectionState` 签名是：

```java
void setWiredDeviceConnectionState(AudioDeviceAttributes attributes, int state, String caller);
// 事务号 64
```

我按这个布局写 Parcel，结果服务端报：

```
IllegalArgumentException: Invalid state 4
```

**原因**：这是 **AOSP 较新分支**的签名。本机 GSI（Android 11，但 framework 来自较早的 Phh 分支）实际用的是**旧版 4 参数签名**：

```java
void setWiredDeviceConnectionState(int device, int state, String address, String caller);
```

**怎么查真实签名**——从设备拉自己的 framework.jar 反编译：

```bash
# 1) 拉 framework.jar
MSYS_NO_PATHCONV=1 adb pull /system/framework/framework.jar

# 2) 解出 dex
jar xf framework.jar          # 得到 classes.dex ~ classes4.dex

# 3) 找含目标类/方法的 dex
for f in classes*.dex; do
  echo "$f: $(dexdump "$f" | grep -c setWiredDeviceConnectionState)"
done

# 4) 导出反汇编，查方法签名
dexdump classes2.dex > c2.txt
grep -A3 "name.*setWiredDeviceConnectionState" c2.txt | head -20

# 输出：
#   type: '(IILjava/lang/String;Ljava/lang/String;)V'    ← 旧版 4 参数
#   type: '(Z)V'                                          ← 上面这个是 AudioManager 的另一个方法

# 5) 同时确认事务号
grep -A5 "TRANSACTION_setWiredDeviceConnectionState" c2.txt
#   value: 64                                            ← 事务号确认无误
```

> **教训：任何跨 binder 的 Parcel 调用，都要先 dump 目标设备的 framework 确认签名，不要照抄 AOSP 文档。** GSI/定制 ROM 的签名经常和 AOSP 主线不一致。

改正后的 Parcel 布局：

```java
data.writeInterfaceToken("android.media.IAudioService");
data.writeInt(8);            // device = DEVICE_OUT_WIRED_HEADPHONE（不是 TYPE_WIRED_HEADPHONES=4!）
data.writeInt(1);            // state = 1 (AVAILABLE) / 0 (UNAVAILABLE)
data.writeString("");        // address
data.writeString("WireFix"); // caller
```

**注意 `8` 和 `4` 的坑**：
- `AudioSystem.DEVICE_OUT_WIRED_HEADPHONE = 8` ← **binder 这里要这个**
- `AudioDeviceInfo.TYPE_WIRED_HEADPHONES = 4` ← 构造 `AudioDeviceAttributes` 时才用这个

我用错过一次，导致 AudioDeviceAttributes 打印成 `bt_a2dp`（type=8 被当成蓝牙）。

### 坑 7（观察）：`app_process` 在 GSI 上不可用

想在免安装的情况下跑 Java（`app_process` / `dalvikvm`），在 Phh GSI 上都会失败：

| 方式 | 结果 |
|------|------|
| `app_process -Djava.class.path=x.jar /system/bin Main` | `Aborted`，jniRegisterNativeMethods 崩 |
| `dalvikvm -cp x.jar Main` | `UnsatisfiedLinkError: SystemProperties.native_get_int` |

**结论**：GSI 上不要指望 app_process，直接做 APK 更省时间。

### 11.3 移植到其他平台

**高通平台（QTI）**
耳机检测不走 ACCDET。常见检测源：

```bash

/sys/class/switch/h2w/state
/sys/devices/virtual/switch/h2w/state
```

改 `service.sh` 里的 `cat` 路径即可。

说明检测链路没问题，问题在 AudioPolicy 层。可以直接只用 App 的 `setForceUse` 兜底（`AudioWire.forceRoute`），不需要补发事件。

**如果 `/data/adb/modules` 不存在（没有 Magisk）**
`MODIFY_AUDIO_ROUTING` 拿不到签名权限，本方案失效。可选路线：
1. 用 `KernelSU` + `susfs`（同样支持 systemless 模块目录布局）
2. 自己编译 system image 把 APK 塞进 priv-app（需要源码环境）
3. 只做"检测 + 提示"，不做实际路由切换

## 结语

这个问题的本质不是"驱动坏了"，而是 **GIS/定制 ROM 的适配缺口**——原厂 vendor 驱动上报的 switch 位与 AOSP 框架的期望不一致，中间少了一层转换。

修复思路可以抽象成一句话：

> **当厂商驱动和 AOSP 框架对不上时，不要试图去改任何一边（通常都改不了），而是在应用层"补发"那个缺失的事件。**

这个思路可以迁移到很多类似的适配问题上：传感器上报格式不对、按键码不一致、充电状态识别错误……只要是"底层有数据、上层不认"，都可以用同样的方式桥接。

祝折腾愉快。
